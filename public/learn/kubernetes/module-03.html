Module 03: Services
DNS & Ingress

Sahil's three API pods are running perfectly and completely unreachable. Every pod has an IP, every one of those IPs changes on restart, and no client can chase them. A Service is Kubernetes' answer: one name and one address that never move, in front of a set of pods that constantly do.

~2h · hands-on heavy builds on Module 02 reach your app, for real Services + Ingress
1

The moving-target problem

Kubernetes gives every pod its own routable IP, and any pod can reach any other pod's IP directly without NAT. That sounds like it solves networking. It does not, for one reason: pod IPs are ephemeral. Every restart, rollout, eviction and reschedule produces a new pod with a new address. Hard-coding one is writing down a phone number that changes hourly.

IPs churn

A rolling update replaces every address in the set within a minute.

The set resizes

Scale from 3 to 10 and seven new endpoints appear. Nobody told the client.

Someone must balance

Even knowing all ten IPs, a client has to choose one, and skip the unhealthy ones.

A Service is a stable front for an unstable set

It has a virtual IP that never changes for its whole life, a DNS name derived from its own name, and a selector that continuously tracks which pods are currently healthy. Pods come and go behind it; the address does not move.

2

What a Service actually is

A Service is not a proxy process sitting somewhere. There is no Service pod. It is a set of routing rules that kube-proxy programs into every node's kernel (iptables or IPVS). Traffic to the Service IP is rewritten to one of the current pod IPs before it leaves the node it started on.

The link from Service to pods is the EndpointSlice: a live list of pod IPs that currently match the selector and pass their readiness probe. This is where Module 02's readiness probe pays off a second time. A pod that fails readiness is silently pulled from this list and receives no traffic.

service.yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  type: ClusterIP
  selector:
    app: api              # must match the POD labels, not the Deployment's name
  ports:
    - name: http
      port: 80             # the Service's own port
      targetPort: http     # the container's port, by NAME
The number one Service bug

The selector must match the labels on the pods, which for a Deployment means spec.template.metadata.labels, not the Deployment's own name or metadata. A selector that matches nothing produces no error at all: just a Service with zero endpoints and a client getting connection refused. Always verify with kubectl get endpointslices -l kubernetes.io/service-name=api.

3

The four types

They are cumulative: NodePort is a ClusterIP plus a node port, LoadBalancer is a NodePort plus a cloud load balancer.

TypeReachable fromUse when
ClusterIP
the default		Inside the cluster onlyAlmost always. Every internal service-to-service call.
NodePortAny node IP on a high port (30000–32767)Local clusters, bare metal, quick external access. Ugly ports, no TLS.
LoadBalancerA real external IPCloud clusters. Provisions a cloud load balancer, and bills you for one per Service.
ExternalNamen/a — a DNS CNAMEGiving an external host (a managed database) an in-cluster name. No proxying at all.
Do not put a LoadBalancer on every service

Each one is a separate cloud load balancer with a separate bill and a separate IP. Ten HTTP services do not need ten load balancers: they need one Ingress controller (itself behind a single LoadBalancer) routing by hostname and path to ten ClusterIP services. That is what the next section is for.

4

port, targetPort, nodePort

Three fields, three different machines, endless confusion. Read them right to left along the path a packet takes.

nodePort: 30080on the NODE (external) port: 80on the SERVICE (cluster-internal) targetPort: 8080on the CONTAINER
FieldLives onWho dials it
nodePortEvery node's IPAnything outside the cluster. NodePort/LoadBalancer only.
portThe Service's ClusterIPOther pods, via DNS: http://api:80.
targetPortThe containerkube-proxy, after rewriting. Defaults to port if omitted.
Use named ports

Set name: http on the container port and put targetPort: http on the Service. Now the app can move from 8080 to 3000 with one edit to the Deployment, and every Service pointing at it keeps working. Numeric targetPorts scattered across a repo are a refactor waiting to break.

5

Cluster DNS: the part that feels like magic

CoreDNS runs in the cluster and gives every Service an automatic name. Every pod's /etc/resolv.conf points at it, with search domains configured so short names resolve.

every form of a service name
# Same namespace: just the service name
http://api

# Another namespace: name.namespace
http://api.payments

# Fully qualified (what the search path expands to)
http://api.payments.svc.cluster.local

#      ^     ^        ^     ^
#      |     |        |     └── cluster domain
#      |     |        └──────── "svc": this is a Service
#      |     └───────────────── namespace
#      └─────────────────────── service name

# Prove it from inside the cluster
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c 'nslookup api; wget -qO- http://api'
This is why namespaces matter for more than tidiness

The same manifest deployed into staging and prod works unchanged, because http://api resolves to the local namespace's Service in each. Cross-namespace calls have to be explicit, which is a useful accident: a hardcoded short name can never silently reach the wrong environment.

Load balancing happens per connection

kube-proxy picks a backend when a connection is established, not per request. A client using HTTP keep-alive or gRPC opens one long-lived connection and pins to a single pod, so scaling up sends it no extra traffic. This surprises teams the first time they scale a gRPC service and see no improvement. The fixes are client-side load balancing, a headless Service, or a proxy that understands HTTP/2.

6

Ingress: one entry point, many services

A Service gives you a layer-4 address. An Ingress gives you layer-7 HTTP routing: hostnames, paths, and TLS termination, all through a single external IP.

An Ingress object does nothing on its own

It is only configuration. Something has to read it: an ingress controller (ingress-nginx, Traefik, HAProxy, or a cloud one) running as pods in your cluster. Apply an Ingress to a cluster with no controller installed and you get no error, no address, and no traffic. This is the most common "my Ingress doesn't work" cause by a wide margin.

ingress.yaml · host and path routing with TLS
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: nginx      # WHICH controller handles this
  tls:
    - hosts: [shop.example.com]
      secretName: shop-tls      # a Secret of type kubernetes.io/tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api          # a ClusterIP Service
                port: { number: 80 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port: { number: 80 }

Ingress and its successor

Ingress is stable, universal, and slightly underpowered: anything beyond host and path routing lives in controller-specific annotations, which are not portable. The Gateway API is the successor and fixes exactly that, with proper typed objects for traffic splitting, headers and cross-namespace routing. Learn Ingress first: it is what almost every existing cluster runs, and the concepts transfer directly.

7

Headless Services and NetworkPolicy

Headless: when you want the pod IPs, not a virtual one

Set clusterIP: None and the Service gets no virtual IP. DNS then returns all matching pod IPs instead of one address, and each pod gets its own DNS record. StatefulSets rely on this so that db-0.db resolves to a specific replica. It is also how a client library does its own load balancing across every backend.

NetworkPolicy: a firewall for pods

By default, every pod can reach every other pod in the cluster, across all namespaces. A NetworkPolicy restricts that, selecting pods by label and declaring what ingress and egress is permitted.

only the api may reach the database
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-api
spec:
  podSelector:
    matchLabels: { app: db }     # these pods are protected
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: api }
      ports:
        - port: 5432
Two things that catch people

First, policies are additive allow rules: the moment any policy selects a pod, everything not explicitly allowed is denied for that direction. Second, they do nothing at all unless your CNI plugin implements them. Calico and Cilium do; a plain kind cluster with the default CNI does not, and your policy will be silently ignored.

8

Debugging the path, in order

When something is unreachable, walk the path from the inside out. Each step eliminates a layer, and you will find the fault in under two minutes instead of guessing.

the networking ladder
# 1. Is the app itself even up? Bypass everything.
kubectl port-forward pod/api-abc123 8080:8080
#    fails → the container is the problem, stop here

# 2. Does the Service have endpoints? THE most common failure.
kubectl get endpointslices -l kubernetes.io/service-name=api
#    empty → selector/label mismatch, OR every pod is failing readiness

# 3. Compare them directly
kubectl get svc api -o jsonpath='{.spec.selector}'; echo
kubectl get pods --show-labels

# 4. Does the Service work from inside the cluster?
kubectl run tmp --rm -it --image=nicolaka/netshoot --restart=Never -- \
  sh -c 'nslookup api; curl -sS -m5 http://api'
#    DNS fails → CoreDNS. curl fails → ports or targetPort wrong.

# 5. Only now look at the Ingress
kubectl describe ingress web
#    ADDRESS empty → no controller is claiming it (ingressClassName?)
kubectl logs -n ingress-nginx deploy/ingress-nginx-controller --tail=50
Empty endpoints is the answer 60% of the time

If you remember one command from this module, make it kubectl get endpointslices. Empty means the Service is pointing at nothing, and there are exactly two causes: labels do not match the selector, or the pods are not passing readiness. Both are two minutes to fix once you know which.

9

Hands-on: expose an app three ways

exercise: ClusterIP, DNS, NodePort, and a broken selector
# 1. Something to expose
kubectl create deployment api --image=nginx:1.27 --replicas=3
kubectl expose deployment api --port=80 --target-port=80

# 2. Confirm the Service found its pods
kubectl get svc api
kubectl get endpointslices -l kubernetes.io/service-name=api

# 3. Reach it by DNS name from another pod
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c 'nslookup api; wget -qO- http://api | head -n4'

# 4. Watch endpoints change live as pods come and go
kubectl get endpointslices -l kubernetes.io/service-name=api -w &
kubectl scale deployment api --replicas=5
kubectl scale deployment api --replicas=2
kill %1

# 5. BREAK IT: point the selector at a label nothing has
kubectl patch svc api -p '{"spec":{"selector":{"app":"typo"}}}'
kubectl get endpointslices -l kubernetes.io/service-name=api  # gone. no error anywhere.
kubectl patch svc api -p '{"spec":{"selector":{"app":"api"}}}'   # fixed

# 6. NodePort, for external access without a cloud
kubectl patch svc api -p '{"spec":{"type":"NodePort"}}'
kubectl get svc api      # note the 3xxxx port

# 7. Clean up
kubectl delete svc api; kubectl delete deployment api
  • You resolved a Service by short name from inside another pod.
  • You watched endpoints appear and vanish as replicas changed.
  • You broke a selector and saw that Kubernetes reported nothing.
  • You can write the fully qualified DNS name of a Service from memory.
  • You can explain why an Ingress with no controller stays address-less.
10

Questions people actually ask

Q1My Service returns connection refused. Where do I start?
Endpoints, always. kubectl get endpointslices -l kubernetes.io/service-name=NAME. Empty means selector-versus-label mismatch or failing readiness probes. Non-empty means the Service is fine and your problem is targetPort, or the app binding 127.0.0.1 instead of 0.0.0.0.
Q2Why is my LoadBalancer Service stuck at Pending?
Because nothing is there to provision one. Cloud clusters have a controller that creates a real load balancer; a local kind or minikube cluster does not, so the external IP stays <pending> forever. Locally, use NodePort, minikube tunnel, or install MetalLB.
Q3Ingress or LoadBalancer?
For HTTP or HTTPS, Ingress, nearly always: one external IP and one certificate setup serving many services, routed by host and path. LoadBalancer is right for non-HTTP protocols (a TCP database port, a game server) or when a service genuinely warrants its own dedicated address.
Q4Can I give a Service a fixed IP?
You can pin spec.clusterIP to an address inside the service CIDR, but do not. The DNS name is the stable contract and the whole point of the abstraction. Hardcoding an IP reintroduces exactly the fragility Services exist to remove.
Q5How do pods on different nodes reach each other at all?
The CNI plugin (Calico, Cilium, Flannel and friends) builds a flat network across nodes, either by routing pod subnets directly or by tunnelling with VXLAN. Kubernetes requires only that every pod can reach every other pod without NAT; how that is achieved is the plugin's business. You almost never touch this layer, which is exactly why it is out of the 80/20.

Module 06: Debugging
& Operations

Everything so far assumed things work. They will not. The difference between an engineer who is comfortable with Kubernetes and one who is not is almost entirely this: a fixed order for finding out what is wrong, and knowing what each failure state actually means rather than guessing at it.

~2h · reference-heavy builds on Modules 01–05 diagnose in under 2 minutes plus Jobs & HPA
1

The five-step playbook

Same five steps, every time, in this order. Do not skip ahead to logs: three quarters of failures never produce a log line, because the container never started.

run these in order, always
# 1. WHAT is broken? Status, restarts, age, node.
kubectl get pods -o wide

# 2. WHY does the cluster say it is broken? Events live at the bottom.
kubectl describe pod POD

# 3. WHAT did the app say? --previous is the crashed instance.
kubectl logs POD
kubectl logs POD --previous
kubectl logs POD -c CONTAINER      # multi-container or init

# 4. WHAT is happening cluster-wide? Scheduling, evictions, image pulls.
kubectl get events --sort-by=.lastTimestamp -A | tail -n 25

# 5. GO INSIDE, only now.
kubectl exec -it POD -- sh
kubectl debug -it POD --image=nicolaka/netshoot --target=CONTAINER
describe before logs, always

An empty logs output tells you almost nothing, and that is the situation for every scheduling failure, image pull failure, mount failure and config error. describe reports all of them, in plain English, in its Events section. Reaching for logs first is the single most common wasted minute in Kubernetes debugging.

2

Every failure state and what it really means

The status column is a diagnosis if you can read it. This table is the module.

StatusActually meansUsual cause & fix
PendingNo node accepted it. The scheduler could not place it.Insufficient CPU/memory, a taint with no toleration, an unbound PVC, or nodeSelector matching nothing. describe pod states which.
ImagePullBackOff
ErrImagePull		The kubelet cannot fetch the image.Typo in name or tag, private registry with no imagePullSecrets, wrong architecture, or rate limiting. Check the exact string in the events.
CrashLoopBackOffContainer starts, exits, restarts, with growing backoff.Your process is exiting. logs --previous. Missing env var, dependency unreachable at boot, or a command that simply completes.
CreateContainerConfigErrorThe container cannot be built from its config.A referenced ConfigMap or Secret, or a specific key inside it, does not exist.
OOMKilled
exit code 137		The kernel killed it for exceeding its memory limit.Raise limits.memory or fix the usage. No log line precedes it; there is no warning before SIGKILL.
Error
exit code 1		The process exited non-zero.An application error. Read the logs.
Running, 0/1 ReadyAlive, but failing readiness.Probe path, port, or a dependency the /readyz endpoint checks. It gets no traffic on purpose.
Init:0/2An init container has not finished.logs POD -c INITNAME. Usually waiting on a dependency that will never arrive.
ContainerCreating (stuck)The kubelet is preparing it and cannot finish.Volume will not mount, a multi-attach conflict on an RWO PVC, or a very slow image pull.
Terminating (stuck)Deletion is blocked.The process ignores SIGTERM and the grace period is long, or a finalizer is waiting. Investigate before force-deleting.
EvictedThe node reclaimed it under pressure.Node out of memory or disk. Pods with no resource requests go first: set them.
The two exit codes worth memorising

137 = 128 + 9 = SIGKILL, which for a container almost always means OOMKilled or a failed liveness probe. 143 = 128 + 15 = SIGTERM, meaning a normal shutdown request during a rollout or scale-down. Seeing 143 in logs during a deploy is not a bug; it is the graceful path working.

3

Events and conditions

Events are the cluster narrating itself: scheduling decisions, pulls, probe failures, evictions. They are also the most under-used data in Kubernetes, largely because they expire.

reading the cluster's own account of events
# Chronological, everywhere. The "what just happened" view.
kubectl get events -A --sort-by=.lastTimestamp | tail -n 30

# Only the bad news
kubectl get events --field-selector type=Warning

# Everything about one object
kubectl get events --field-selector involvedObject.name=api-7d4f-x9k2

# Live stream while you reproduce the problem
kubectl get events -w
Events expire after about an hour

Default TTL is 60 minutes, so a failure from last night has left no trace by morning. This is precisely why clusters ship events to a real logging system. If you are debugging something intermittent, start kubectl get events -w before you reproduce it.

Conditions are the other half: structured booleans on the object itself, better for automation than the human-readable status column.

conditions, for scripts and for precision
kubectl get pod POD -o jsonpath='{.status.conditions}' | jq
PodScheduled=True  Initialized=True  ContainersReady=False  Ready=False

# Block until something is true, instead of sleeping and hoping
kubectl wait --for=condition=Ready pod/POD --timeout=120s
kubectl wait --for=condition=Available deployment/api --timeout=120s
4

kubectl debug: tools without rebuilding the image

Your production image is distroless, so exec finds no shell. That is correct security, and it used to mean rebuilding a "debug" image to investigate anything. Ephemeral containers fixed it.

three shapes of kubectl debug
# A. Attach a toolbox container INTO a running pod. Shares its network
#    namespace, and with --target, its process namespace too.
kubectl debug -it api-7d4f --image=nicolaka/netshoot --target=api
#    now: dig, curl, ss, tcpdump, nslookup — against the real pod's network

# B. Copy a crash-looping pod and change the command, so it stays up
kubectl debug api-7d4f -it --copy-to=api-debug -- sh
#    same image, same env, same mounts — but a shell instead of the app

# C. Get a root shell ON a node (for node-level problems)
kubectl debug node/dev-worker -it --image=busybox:1.36
#    the node's filesystem is mounted at /host
Option B is the one that saves your afternoon

A CrashLoopBackOff you cannot reproduce locally is nearly impossible to inspect: the container is only alive for a second at a time. --copy-to gives you a clone with identical image, environment, secrets and volumes, but running a shell, so you can check what the app would have seen. That is usually a missing env var or an unreadable mounted file, and it is visible in ten seconds.

5

When the problem is the node

Sometimes nothing is wrong with your pod. Check the machine.

node-level checks
kubectl get nodes
kubectl describe node dev-worker
#    Conditions: MemoryPressure, DiskPressure, PIDPressure, Ready
#    Allocated resources: how full it already is
#    Taints: what it refuses to run

# Live usage (needs metrics-server installed)
kubectl top nodes
kubectl top pods --sort-by=memory -A

# Taking a node out of service safely, in the right order
kubectl cordon dev-worker                    # no NEW pods land here
kubectl drain dev-worker --ignore-daemonsets \
  --delete-emptydir-data                       # evict existing pods politely
# ...maintenance...
kubectl uncordon dev-worker
Taints and tolerations, in one line

A taint on a node repels pods; a matching toleration on a pod lets it stay anyway. That is how control plane nodes stay free of your workloads, and how GPU nodes are reserved for jobs that need them. A pod stuck Pending with "had untolerated taint" in its events is this, and only this.

6

Jobs and CronJobs

Not everything is a server. A Job runs pods until they succeed and then stops. A CronJob creates Jobs on a schedule.

a migration Job and a nightly CronJob
apiVersion: batch/v1
kind: Job
metadata: { name: migrate }
spec:
  backoffLimit: 3              # retries before giving up
  activeDeadlineSeconds: 600    # hard timeout for the whole Job
  ttlSecondsAfterFinished: 3600 # auto-clean 1h after it finishes
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: migrate
          image: ghcr.io/acme/api:1.4.2
          command: ['./manage', 'migrate']
---
apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-backup }
spec:
  schedule: "0 3 * * *"            # 03:00 daily, cluster timezone
  concurrencyPolicy: Forbid       # never overlap with a slow previous run
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: ghcr.io/acme/backup:2.1
Four settings that turn a CronJob from a liability into a tool

concurrencyPolicy: Forbid stops a slow run from stacking on the next one. activeDeadlineSeconds stops a hung job running forever. ttlSecondsAfterFinished stops completed pods accumulating for weeks. And make the job idempotent, because a CronJob's guarantee is at least once, not exactly once.

7

Autoscaling

Three different scalers, often confused with each other. Only the first is in the everyday 80/20.

HPA

Changes the number of pods based on CPU, memory or custom metrics. The one you will actually use.

VPA

Changes the requests and limits of pods. Useful for right-sizing; conflicts with HPA on the same metric.

Cluster Autoscaler

Changes the number of nodes when pods cannot be scheduled. Cloud only.

a horizontal pod autoscaler
kubectl autoscale deployment api --min=2 --max=10 --cpu-percent=70
kubectl get hpa -w

# Equivalent, and version-controllable
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
HPA needs two things you may not have

First, metrics-server must be running, or the HPA reports <unknown> and never scales. Second, the target percentage is measured against the CPU request, so a pod with no CPU request gives the HPA nothing to compute against. No requests, no autoscaling. This is one more reason Module 02 insisted on setting them.

8

Hands-on: break five things, diagnose each

Do not read ahead to the cause. For each one, run the playbook and name the fault before you fix it.

exercise: five deliberate failures
# FAULT 1 — a bad image reference
kubectl run f1 --image=nginx:definitely-not-a-tag

# FAULT 2 — a process that exits immediately
kubectl run f2 --image=busybox:1.36 -- sh -c 'echo boom; exit 1'

# FAULT 3 — a missing ConfigMap
kubectl run f3 --image=busybox:1.36 --overrides='{"spec":{"containers":[{"name":"f3","image":"busybox:1.36","command":["sleep","3600"],"envFrom":[{"configMapRef":{"name":"does-not-exist"}}]}]}}'

# FAULT 4 — unschedulable: asks for more CPU than any node has
kubectl run f4 --image=nginx:1.27 --overrides='{"spec":{"containers":[{"name":"f4","image":"nginx:1.27","resources":{"requests":{"cpu":"200"}}}]}}'

# FAULT 5 — memory limit far below what the process wants
kubectl run f5 --image=polinux/stress --restart=Never \
  --limits=memory=32Mi -- stress --vm 1 --vm-bytes 250M --timeout 60s

# ── Now diagnose. For each pod, in order: ──
kubectl get pods
kubectl describe pod f1 | tail -n 12
kubectl logs f2 --previous
kubectl describe pod f3 | grep -i -A3 'config'
kubectl describe pod f4 | grep -i -A3 'events'
kubectl describe pod f5 | grep -A4 'Last State'

# Expected: 1 ImagePullBackOff · 2 CrashLoopBackOff · 3 CreateContainerConfigError
#           4 Pending/Insufficient cpu · 5 OOMKilled (137)

kubectl delete pod f1 f2 f3 f4 f5 --ignore-not-found
  • You named each of the five faults from describe alone.
  • You found exit code 137 and know which of the five produced it.
  • You can recite the five-step playbook without looking.
  • You used kubectl debug at least once.
  • You know why an HPA shows <unknown>.
9

Questions people actually ask

Q1A pod is stuck Terminating. Can I force it?
You can (--force --grace-period=0) but find out why first. The API object disappears while the container may keep running on the node, which for anything holding a volume or a lock is worse than the stuck pod. Real causes: the app ignores SIGTERM, a finalizer is waiting on cleanup, or the node is unreachable. Only the last genuinely justifies force.
Q2How do I see logs from a pod that no longer exists?
You cannot, from Kubernetes. kubectl logs reads files on the node, and they go when the pod does. --previous only reaches the immediately preceding container of a still-existing pod. This gap is the entire argument for shipping logs off-cluster (Loki, Elasticsearch, a cloud logging service) before you need them.
Q3Everything looks healthy but the app is slow.
Check CPU throttling first: a container at its CPU limit is throttled, not killed, so every Kubernetes-level indicator stays green while latency triples. kubectl top pod next to the configured limit, and the container_cpu_cfs_throttled_seconds_total metric if you have Prometheus. This is the most common "nothing is wrong but it is slow" cause.
Q4Why does my Job keep creating pods?
It is retrying, because the pod exits non-zero, up to backoffLimit (default 6). Each attempt is a new pod, which is why you see several. Read the logs of the first failed pod, not the last: later attempts often fail differently because of partial state left by the earlier ones.
Q5What single command gives the best overview of a sick cluster?
kubectl get pods -A --field-selector=status.phase!=Running shows everything that is not healthy, cluster-wide, in one screen. Follow it with kubectl get events -A --sort-by=.lastTimestamp | tail -30. Those two commands together answer "what is broken and what happened" in about five seconds.

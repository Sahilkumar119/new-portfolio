Configuration · Kubernetes · Day 4

Module 04: Config
& Secrets

Sahil has one image that must run in dev, staging and production. Baking three sets of settings into three images defeats the entire point of a container. This module separates the two: the image is what the app is, ConfigMaps and Secrets are where it happens to be running.

~1.5h · hands-on builds on Module 02 one image, many environments plus honest secret handling
1

Config belongs outside the image

An image that contains a production database URL is not portable, cannot be tested honestly, and leaks credentials to anyone who can pull it. The rule is old and still correct: build once, deploy anywhere, inject the difference at runtime.

ConfigMap

Non-sensitive key/value data or whole config files. Stored in plain text, and that is fine.

Secret

The same thing, with base64 encoding, tighter defaults, and optional encryption at rest.

Downward API

Values the cluster already knows: pod name, namespace, node, labels, resource limits.

Both cap out at 1MiB

ConfigMaps and Secrets are stored in etcd, which is not a file server. The 1MiB ceiling is a hint about intent: settings, certificates and small config files, yes; datasets, binaries and ML models, no. Those belong in a volume or an object store.

2

ConfigMaps

A ConfigMap holds either short values or entire file contents, and the two coexist happily in one object.

configmap.yaml · values and a whole file
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
data:
  # simple values → become env vars nicely
  LOG_LEVEL: "info"
  FEATURE_CHECKOUT_V2: "true"
  DB_HOST: "postgres.data.svc.cluster.local"

  # a whole file → mount this one as a volume
  app.properties: |
    server.port=8080
    cache.ttl=300
    retries=3
generating them without hand-writing YAML
# From literals
kubectl create configmap api-config \
  --from-literal=LOG_LEVEL=info --from-literal=DB_HOST=postgres

# From a file (key = filename, value = contents)
kubectl create configmap api-config --from-file=app.properties

# From a .env file (each line becomes its own key)
kubectl create configmap api-config --from-env-file=.env

# The pattern for updating one that already exists, idempotently
kubectl create configmap api-config --from-file=app.properties \
  --dry-run=client -o yaml | kubectl apply -f -
3

Two ways to consume: env vars or files

The choice looks cosmetic and is not. It decides whether a config change can ever reach a running pod.

Environment variablesMounted volume
Updates on change?No. Fixed at container start, forever.Yes, files refresh within about a minute.
Good forShort scalar settings, feature flags, hostnamesConfig files, certificates, anything multiline
Visible inkubectl describe pod, crash dumps, child processesOnly the filesystem
Secrets?Workable but leakierPreferred. Files can be tmpfs and are not inherited by subprocesses.
all three consumption patterns in one pod spec
spec:
  containers:
    - name: api
      image: ghcr.io/acme/api:1.4.2

      # A. every key in the ConfigMap becomes an env var
      envFrom:
        - configMapRef: { name: api-config }
        - secretRef:    { name: api-secrets }

      # B. one key, renamed (useful when names clash)
      env:
        - name: DATABASE_PASSWORD
          valueFrom:
            secretKeyRef:
              name: api-secrets
              key: db-password

      # C. mounted as files — the only form that can update live
      volumeMounts:
        - name: config
          mountPath: /etc/app
          readOnly: true

  volumes:
    - name: config
      configMap:
        name: api-config
        items:                       # optional: pick specific keys
          - key: app.properties
            path: app.properties   # → /etc/app/app.properties
Mounting over a directory hides it

A volumeMount at /etc/app replaces that directory entirely. Anything the image shipped there is now invisible. If you only mean to add one file next to existing ones, use subPath. The catch: a subPath mount never receives updates, so you have traded live reload for coexistence.

4

Secrets

Structurally a Secret is a ConfigMap with base64 values and a type. Practically it is treated differently by the API server, by RBAC conventions, and by anything that scans your cluster.

creating secrets · use stringData, not base64 by hand
# From the CLI (never lands in a file, but does land in shell history)
kubectl create secret generic api-secrets \
  --from-literal=db-password='s3cr3t'

# From a file, which keeps it out of your history entirely
kubectl create secret generic api-secrets --from-file=db-password=./pw.txt

# A TLS secret, for an Ingress
kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key

# Registry credentials for private images
kubectl create secret docker-registry ghcr \
  --docker-server=ghcr.io --docker-username=sahil --docker-password="$TOKEN"
# → then in the pod spec: imagePullSecrets: [{name: ghcr}]

# In YAML: stringData takes plain text and encodes it for you
apiVersion: v1
kind: Secret
metadata: { name: api-secrets }
type: Opaque
stringData:
  db-password: "s3cr3t"
TypeFor
OpaqueAnything. The default.
kubernetes.io/tlsCertificate and key pairs. Required by Ingress TLS.
kubernetes.io/dockerconfigjsonPrivate registry credentials, via imagePullSecrets.
kubernetes.io/service-account-tokenAPI tokens. Mostly automatic now. Module 07.
5

The uncomfortable truth about Secrets

base64 is encoding, not encryption

A Secret is plainly readable by anyone who can read it. There is no key, no password, no protection. base64 -d is the entire attack. Kubernetes uses base64 so binary data survives YAML, and for no security reason at all. Treat "it is in a Secret" as meaning "it is stored, labelled sensitive", not "it is safe".

thirty seconds to read any secret you have access to
kubectl get secret api-secrets -o jsonpath='{.data.db-password}' | base64 -d
s3cr3t

# Or all of it at once
kubectl get secret api-secrets -o go-template='{{range $k,$v := .data}}{{$k}}: {{$v | base64decode}}{{"\n"}}{{end}}'

What actually protects a secret

ControlWhat it stops
RBAC on the secrets resourceThe main defence. Very few humans and service accounts should be able to get secrets. Module 07.
Encryption at rest in etcdSomeone reading etcd's disk. Off by default on self-managed clusters.
Never commit themThe most common real-world leak by far. Use Sealed Secrets or SOPS if secrets must live in git.
External secret managersVault, AWS Secrets Manager, or the Secrets Store CSI driver: the secret is fetched at mount time and never stored in etcd.
Mount as files, not envEnv vars appear in describe pod output, crash reports, and every child process.
Anyone with exec is anyone with your secrets

If a person can run kubectl exec into a pod, they can read every secret that pod mounts, regardless of how carefully the Secret object itself is locked down. Access to a workload is access to its credentials. Plan RBAC accordingly.

6

Making a config change actually take effect

You edit a ConfigMap, apply it, and nothing changes. This is expected behaviour and it catches everyone once.

How consumedAfter you change the ConfigMap
env / envFromNothing happens, ever. The variable was set at container start.
volume mountThe file updates within roughly a minute. Your app still has to re-read it.
volume mount with subPathNothing happens, ever.

So the honest options are: restart the pods, or make the app watch the file. Restarting is simpler and almost always correct.

two ways to pick up new config
# Manual: roll the Deployment. Safe, uses the normal rolling update.
kubectl rollout restart deployment/api

# Automatic: put a hash of the config INTO the pod template, so any
# config change becomes a template change → a normal rollout.
spec:
  template:
    metadata:
      annotations:
        checksum/config: "a3f9c2e1..."   # CI computes this from the file
Immutable ConfigMaps and Secrets

Set immutable: true and the object can never be edited, only replaced under a new name. That sounds restrictive and is a real win: it removes the entire "did this pod get the old config or the new one?" class of mystery, and it measurably reduces API server load in large clusters. Pair it with versioned names like api-config-v7 referenced from the Deployment.

7

The Downward API

Some configuration is not yours to write: the pod's own name, its namespace, its node, its memory limit. The downward API injects those without you hardcoding anything.

values the cluster already knows
env:
  - name: POD_NAME
    valueFrom:
      fieldRef: { fieldPath: metadata.name }
  - name: POD_NAMESPACE
    valueFrom:
      fieldRef: { fieldPath: metadata.namespace }
  - name: NODE_NAME
    valueFrom:
      fieldRef: { fieldPath: spec.nodeName }
  - name: MEMORY_LIMIT
    valueFrom:
      resourceFieldRef: { containerName: api, resource: limits.memory }
Where this earns its keep

Two places, constantly. Structured logging: tagging every line with pod and node makes a hundred replicas searchable. Runtime sizing: a JVM or Node process reading its own memory limit can set its heap to fit, instead of discovering the limit by being OOMKilled.

8

Hands-on: inject, decode, reload

exercise: prove which config updates live and which does not
# 1. A ConfigMap and a Secret
kubectl create configmap demo-cfg --from-literal=GREETING=hello --from-literal=MODE=dev
kubectl create secret generic demo-sec --from-literal=TOKEN=abc123

# 2. A pod that consumes both, as env AND as files
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: cfgdemo }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ['sh','-c','sleep 3600']
      envFrom:
        - configMapRef: { name: demo-cfg }
        - secretRef: { name: demo-sec }
      volumeMounts:
        - { name: cfg, mountPath: /etc/cfg }
  volumes:
    - name: cfg
      configMap: { name: demo-cfg }
EOF

# 3. See both forms arrive
kubectl exec cfgdemo -- sh -c 'echo "$GREETING / $TOKEN"; ls /etc/cfg; cat /etc/cfg/MODE'

# 4. Decode the "secret" yourself. This is the point of section 5.
kubectl get secret demo-sec -o jsonpath='{.data.TOKEN}' | base64 -d; echo

# 5. Change the ConfigMap and watch what does and does not update
kubectl create configmap demo-cfg --from-literal=GREETING=goodbye --from-literal=MODE=prod \
  --dry-run=client -o yaml | kubectl apply -f -

#    wait ~60s, then:
kubectl exec cfgdemo -- sh -c 'echo "env: $GREETING"; echo "file: $(cat /etc/cfg/GREETING)"'
#    env: hello    ← STALE, fixed at container start
#    file: goodbye ← updated

# 6. Clean up
kubectl delete pod cfgdemo; kubectl delete cm demo-cfg; kubectl delete secret demo-sec
  • You saw an env var stay stale while the mounted file updated.
  • You decoded a Secret in one command and understand what that implies.
  • You can name two ways to make a config change reach running pods.
  • You know why subPath mounts never refresh.
  • You can say what actually protects a secret, and it is not base64.
9

Questions people actually ask

Q1Should I use env vars or mounted files?
Env vars for short settings your app reads once at startup, which is most of them. Files for anything multiline, anything you want to change without a restart, and anything sensitive. When in doubt, env for ConfigMaps and files for Secrets is a defensible default.
Q2Can I put Secrets in git?
Not as plain Secret manifests: the base64 is decorative and your repository is now a credential store. Options that do work: Sealed Secrets (encrypted with a cluster-held key, safe to commit), SOPS with age or KMS, or External Secrets Operator, where git holds only a reference and the real value stays in Vault or a cloud secret manager.
Q3Why did my pod fail with CreateContainerConfigError?
A referenced ConfigMap or Secret does not exist, or the specific key you named is missing. The pod schedules fine and then the kubelet cannot build the container. kubectl describe pod names the exact missing object. Usually a typo, or applying the Deployment before the ConfigMap.
Q4How do I do per-environment config without duplicating everything?
A base set of manifests plus a small per-environment overlay. Kustomize is built into kubectl (kubectl apply -k) and has configMapGenerator, which also hashes the ConfigMap name so a config change automatically triggers a rollout. Helm does the same job with templating and a values file. Module 07 compares them.
Q5Can a pod read a ConfigMap from another namespace?
No. ConfigMaps and Secrets are namespaced and a pod can only reference ones in its own namespace. There is no cross-namespace reference by design: it would quietly break the isolation boundary. Duplicate it, or use a controller like Reflector that syncs copies deliberately.

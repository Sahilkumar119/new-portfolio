Module 05: Storage
& StatefulSets

Sahil's Postgres pod restarted overnight and came back empty. Nothing malfunctioned: a container filesystem dies with its container, and that is by design. This module is how you keep the parts that must survive, and how to give a workload a stable identity when interchangeable replicas are not enough.

~1.5h · hands-on builds on Module 02 data that outlives pods PVC + StatefulSet
1

Pods forget everything

A container's writable layer is deleted when the container is. Restart a container and the layer is fresh. Reschedule the pod to another node and even the node's disk is gone. Kubernetes never repairs a pod, so anything valuable must live outside the pod's lifecycle.

container writable layerdies with the container
emptyDir volumedies with the pod
PersistentVolumeoutlives the pod, and usually the cluster
Three lifetimes, and you must pick one deliberately

Scratch space that can vanish on restart: emptyDir. Data that must survive a reschedule to a different node: PersistentVolumeClaim. Config and credentials: ConfigMap and Secret from Module 04, which are also mounted as volumes. Everything else is a variation on these.

the classic emptyDir use: two containers, one directory
spec:
  containers:
    - name: app
      image: ghcr.io/acme/api:1.4.2
      volumeMounts:
        - { name: logs, mountPath: /var/log/app }
    - name: shipper              # sidecar reads what the app writes
      image: fluent/fluent-bit:3.1
      volumeMounts:
        - { name: logs, mountPath: /var/log/app, readOnly: true }
  volumes:

hostPath is a security hole and a scheduling trap

It mounts a path from the node into your pod. A hostPath of / or the container runtime socket is a straightforward container escape, which is why Pod Security Admission blocks it in restricted namespaces. It also silently pins your pod to whichever node happened to have the data, and the next reschedule finds an empty directory. Legitimate uses are node-level agents. Application data is never one of them.

Dynamic provisioning is the normal path

You almost never write a PV. You write a PVC, the StorageClass's CSI driver creates the real disk, and a PV appears bound to your claim. Check what your cluster offers with kubectl get storageclass: the one marked (default) is used when you omit storageClassName.

A PVC stuck in Pending

Three usual causes, in order of likelihood: no default StorageClass exists and you did not name one; the requested access mode is not supported by that class; or volumeBindingMode: WaitForFirstConsumer, where the PVC deliberately stays Pending until a pod actually uses it, so the volume is created in the right zone. The third is correct behaviour, not a fault.

4

Access modes and reclaim policies

Access modes: who can mount it, and how many

ModeMeansReality
ReadWriteOnce (RWO)Read-write by pods on one nodeWhat block storage gives you (EBS, GCE PD, most local). The default and the common case.
ReadWriteMany (RWX)Read-write from many nodesNeeds a shared filesystem: NFS, EFS, CephFS, Azure Files. Block storage cannot do this.
ReadOnlyMany (ROX)Read-only from many nodesShared static assets, reference data.
ReadWriteOncePodExactly one pod, cluster-wideStrict single-writer guarantee. Stable since v1.29.
The RWO scaling trap

Scale a Deployment with an RWO volume to replicas: 3 and the extra pods hang in ContainerCreating forever with a multi-attach error, because the volume can only attach to one node. RWO is not "one pod": it is "one node", so replicas that land together may work while the rest never start, which is worse than a clean failure. If several pods genuinely need the same data, you need RWX storage or a StatefulSet giving each pod its own volume.

Reclaim policy: what happens when the PVC is deleted

PolicyOn PVC deletion
DeleteThe PV and the underlying disk are destroyed. The default for most dynamic classes.
RetainThe PV survives in Released state; the data is kept and an admin must reclaim it manually.
Check this before your first production database

With the default Delete policy, kubectl delete pvc is irreversible data loss, and it takes about a second. For anything you would miss, use a StorageClass with reclaimPolicy: Retain, and take real backups: a Retain policy is a safety catch, not a backup strategy.

5

StatefulSets: when pods need identity

A Deployment's pods are interchangeable and randomly named. Some workloads cannot work that way: a database replica set needs to know that db-0 is the primary, and each member needs its own disk that follows it across restarts.

DeploymentStatefulSet
Pod namesRandom: api-7d4f-x9k2Ordinal and stable: db-0, db-1
Start orderAll at onceSequential: db-1 waits for db-0 to be Ready
StorageAll pods share one PVC, if anyOne PVC per pod, created automatically, reattached by name
DNSThe Service name onlyPer-pod: db-0.db.ns.svc.cluster.local
Scale downAny podHighest ordinal first, and PVCs are kept
statefulset.yaml · note volumeClaimTemplates
apiVersion: v1
kind: Service
metadata: { name: db }
spec:
  clusterIP: None              # headless: gives each pod its own DNS name
  selector: { app: db }
  ports: [{ port: 5432 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db }
spec:
  serviceName: db               # must point at the headless Service
  replicas: 3
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:17
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:            # one PVC per pod: data-db-0, data-db-1, ...
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 10Gi } }
Deleting a StatefulSet does not delete its data

The PVCs created by volumeClaimTemplates are deliberately left behind, so recreating the StatefulSet reattaches every pod to its original volume by name. This is a feature and a surprise: those volumes keep costing money until someone deletes them. Audit with kubectl get pvc after tearing down any stateful workload.

6

Should this even run in Kubernetes?

You now know how to run a database in a cluster. The harder question is whether to.

Reasonable in-cluster

Caches you can rebuild, dev and test databases, queues with replication, anything whose loss is an inconvenience rather than an incident.

Think hard first

The production database of record. Backups, point-in-time recovery, failover, version upgrades and storage performance are all now your job.

The honest default

For most teams, a managed database (RDS, Cloud SQL, Neon) reached from the cluster over an ExternalName Service or plain DNS beats a self-run StatefulSet on every axis except cost curiosity. Running Postgres yourself is genuinely doable with a mature operator like CloudNativePG, but it is an ongoing commitment, not a one-off manifest. Choose it deliberately, not by momentum.

Hands-on: lose data, then keep it

exercise: prove persistence, then prove identity
# 1. What storage does this cluster offer?
kubectl get storageclass

# 2. Claim some, and use it
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: demo-data }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
---
apiVersion: v1
kind: Pod
metadata: { name: writer }
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ['sh','-c','sleep 3600']
      volumeMounts: [{ name: d, mountPath: /data }]
  volumes:
    - name: d
      persistentVolumeClaim: { claimName: demo-data }
EOF

kubectl get pvc,pv

# 3. Write to both places: the PVC and the container's own filesystem
kubectl exec writer -- sh -c 'echo persisted > /data/file; echo ephemeral > /tmp/file'

# 4. Destroy the pod and recreate it against the SAME claim
kubectl delete pod writer
kubectl apply -f - <<'EOF'
# (same Pod manifest as above)
EOF

# 5. The verdict
kubectl exec writer -- sh -c 'cat /data/file; cat /tmp/file 2>&1'
persisted
cat: can't open '/tmp/file': No such file or directory

# 6. StatefulSet identity: note the names and the auto-created PVCs
kubectl create service clusterip web --tcp=80:80 --dry-run=client -o yaml \
  | sed 's/clusterIP: .*/clusterIP: None/' | kubectl apply -f -
# apply a StatefulSet using serviceName: web, then:
kubectl get pods -l app=web     # web-0, web-1 — ordered, stable
kubectl get pvc                 # one per pod

# 7. Clean up (note: PVCs must be deleted explicitly)
kubectl delete pod writer; kubectl delete pvc demo-data
  • A file on a PVC survived pod deletion; a file in the container did not.
  • You can explain why RWO breaks a multi-replica Deployment.
  • You checked your cluster's reclaim policy before trusting it with data.
  • You saw StatefulSet pods get ordered names and one PVC each.
  • You know that deleting a StatefulSet leaves its PVCs behind.
8

Questions people actually ask

Q1My PVC is stuck Pending. What now?
kubectl describe pvc NAME and read the events. In order: is there a default StorageClass (kubectl get sc)? Does the class support the access mode you asked for? Is volumeBindingMode: WaitForFirstConsumer set, in which case Pending is normal until a pod schedules? Is the class out of quota?
Q2Can several pods share one PVC?
Only if the storage supports ReadWriteMany, which means a shared filesystem (NFS, EFS, CephFS), not block storage. And even then, ask whether you want it: concurrent writers to a shared filesystem need application-level coordination. Usually the right answer is one volume per pod via a StatefulSet, or moving shared data to object storage.
Q3How do I resize a volume?
If the StorageClass has allowVolumeExpansion: true, edit the PVC's spec.resources.requests.storage upward and apply. The filesystem grows, sometimes only after the pod restarts. Shrinking is not supported at all: that path is backup, new smaller PVC, restore.
Q4Why is my PVC stuck Terminating?
A finalizer is protecting it because a pod still uses it. Delete the pod first and the PVC finishes. Force-removing the finalizer leaks the real cloud disk, which then bills you silently forever, so find the pod instead: kubectl get pods -o json | grep -l CLAIMNAME.
Q5Deployment with a PVC, or StatefulSet?
One replica that needs one volume: a Deployment with a PVC is simpler and fine, as long as you set strategy: Recreate so the old pod releases the volume before the new one wants it. Multiple replicas each needing their own volume, or any need for stable network identity: StatefulSet. Do not use a StatefulSet just because the app happens to store something.

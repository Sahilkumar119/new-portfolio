Module 07: Production
& Security

Everything Sahil has built so far works. None of it is safe. Containers run as root, any pod can call the API server, one runaway namespace can starve the cluster, and a node drain takes the service down. This module closes those gaps, and ends with the checklist you run before anything reaches production.

~2h · final module builds on everything demo → deployable RBAC + hardening
1

Namespaces, quotas, limit ranges

A namespace is a name scope. On its own it is organisational, not protective. It becomes a real boundary once you attach RBAC, quotas and network policies to it.

a namespace that cannot eat the cluster
apiVersion: v1
kind: ResourceQuota
metadata: { name: team-quota, namespace: team-a }
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.memory: "40Gi"
    persistentvolumeclaims: "10"
    count/pods: "50"
---
apiVersion: v1
kind: LimitRange            # defaults for pods that specify nothing
metadata: { name: defaults, namespace: team-a }
spec:
  limits:
    - type: Container
      default:        { cpu: "500m", memory: "512Mi" }
      defaultRequest: { cpu: "100m", memory: "128Mi" }
A ResourceQuota changes the rules for everyone in the namespace

Once a quota constrains CPU or memory, every pod in that namespace must declare requests and limits or creation is rejected outright. That breaks existing manifests immediately, which is exactly why you pair a quota with a LimitRange: the LimitRange supplies defaults so old workloads keep deploying while the quota does its job.

2

RBAC

Four objects, one sentence: a Role lists permissions, a Binding gives that Role to someone. The only variation is whether the scope is one namespace or the whole cluster.

ObjectScopeSays
RoleOne namespace"These verbs, on these resources"
ClusterRoleCluster-wideSame, but also covers cluster-scoped objects (nodes, PVs)
RoleBindingOne namespace"This subject gets that Role, here"
ClusterRoleBindingCluster-wide"This subject gets that ClusterRole, everywhere"
read-only access to pods, in one namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: team-a }
rules:
  - apiGroups: [""]              # "" is the core group
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: devs-read-pods, namespace: team-a }
subjects:
  - kind: ServiceAccount
    name: ci-runner
    namespace: team-a
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
the command that answers every RBAC question
# Can I?
kubectl auth can-i delete pods -n team-a

# Can THAT service account? (this is the one you actually want)
kubectl auth can-i list secrets \
  --as=system:serviceaccount:team-a:ci-runner -n team-a

# Everything a subject can do, in one listing
kubectl auth can-i --list --as=system:serviceaccount:team-a:ci-runner
cluster-admin is not a starting point

Binding cluster-admin to a service account "until we work out the permissions" is how most clusters end up permanently over-privileged. Start with nothing, run the workload, read the Forbidden errors, and add exactly those verbs. It takes twenty extra minutes once. Pay particular attention to secrets: read access there is read access to every credential in the namespace, and to pods/exec, which is equivalent.

3

Service accounts

Every pod runs as a ServiceAccount. If you do not name one, it gets default in its namespace, and a token for it is mounted into the container at /var/run/secrets/kubernetes.io/serviceaccount. Most applications never call the Kubernetes API and should not carry that token at all.

stop mounting API tokens into apps that do not need them
apiVersion: v1
kind: ServiceAccount
metadata: { name: api }
automountServiceAccountToken: false   # default for this SA
---
# ...or per pod, which overrides the SA setting
spec:
  serviceAccountName: api
  automountServiceAccountToken: false
Why this matters more than it looks

An attacker who gets code execution in your container immediately looks for that token. With it, they can do whatever the service account can do, from inside your network. Turning off automounting for every workload that does not talk to the API removes that first step entirely, and costs one line.

4

securityContext: the five lines that matter

By default a container runs as root, with a writable root filesystem, and the ability to gain new privileges. None of that is needed by a typical application.

a hardened container, and nothing exotic
spec:
  securityContext:                   # pod level
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001                   # group that owns mounted volumes
    seccompProfile: { type: RuntimeDefault }
  containers:
    - name: api
      image: ghcr.io/acme/api@sha256:9f2c...
      securityContext:               # container level, wins on conflict
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:                  # give back only what must be writable
        - { name: tmp, mountPath: /tmp }
  volumes:
    - name: tmp
      emptyDir: {}
SettingStops
runAsNonRoot: trueRunning as UID 0. The pod fails to start rather than silently running as root, which is the point.
readOnlyRootFilesystem: trueAn attacker writing tools or a webshell into the image. Mount an emptyDir wherever the app genuinely writes.
allowPrivilegeEscalation: falsesetuid binaries gaining privileges the parent did not have.
capabilities.drop: ["ALL"]Every Linux capability. Add back only what you can name a reason for.
seccompProfile: RuntimeDefaultMost of the kernel syscall surface. Nearly free, and blocks whole classes of escape.
Two things that break when you turn these on

readOnlyRootFilesystem breaks apps that write temp files, caches or PID files: find the paths and mount an emptyDir at each. runAsNonRoot breaks images that assume root, most commonly nginx binding port 80, since ports under 1024 need privileges. Use an unprivileged image variant listening on 8080, and let the Service map 80 to it.

5

Pod Security Admission

Setting a good securityContext on your own pods is optional discipline. PSA makes it enforced policy at the namespace level, and it is built in: no controller to install.

LevelAllows
privilegedEverything. The default if you set nothing.
baselineBlocks the well-known escapes: privileged containers, host namespaces, most hostPath mounts.
restrictedEnforces non-root, dropped capabilities, no privilege escalation, seccomp. The target for application namespaces.
roll it out safely: warn first, enforce later
# Step 1: find out what WOULD break, breaking nothing
kubectl label namespace team-a \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

# Step 2: fix the manifests the warnings named, then enforce
kubectl label namespace team-a \
  pod-security.kubernetes.io/enforce=restricted --overwrite
Warn, then audit, then enforce

Enforcing restricted on a live namespace rejects every non-compliant pod immediately, which during a rollout means an outage. The warn-and-audit labels give you the same list of violations with zero risk. There is never a good reason to skip that step.

6

Staying available during disruption

Your Deployment survives a crash. It does not automatically survive an administrator: a node drain for an upgrade will happily evict all three of your replicas at once if nothing says otherwise.

PodDisruptionBudget + graceful shutdown
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: api }
spec:
  minAvailable: 2              # or maxUnavailable: 1
  selector:
    matchLabels: { app: api }
---
# ...and in the pod spec, so shutdown is not abrupt
spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: api
      lifecycle:
        preStop:
          exec: { command: ["sleep", "5"] }   # let endpoints drain first
Why the preStop sleep is not a hack

When a pod is deleted, two things happen in parallel: the kubelet sends SIGTERM, and the endpoint controller removes the pod from Service endpoints. They race, and kube-proxy on every node takes a moment to catch up, so in-flight requests can arrive at a process already shutting down. A short preStop sleep lets endpoint removal win the race. It is the standard fix for "we get 502s during every deploy".

A PDB can also block maintenance forever

minAvailable: 1 on a single-replica Deployment means a drain can never evict it, and the node upgrade hangs. Budgets are a contract: they only work if you have enough replicas to honour them. One replica plus a PDB is a deadlock, not a guarantee.

7

Scheduling control

Three mechanisms, from blunt to precise. In practice you use the last one and occasionally the first.

MechanismSays
nodeSelector"Only nodes with this label." Simple, exact, no flexibility.
Taints & tolerationsNode side: "keep everything off me unless it tolerates this." For GPU nodes, dedicated pools, and control plane nodes.
Affinity / anti-affinityPod side, expressive: required or preferred, based on node labels or on where other pods already are.
spread replicas across nodes, so one node loss is survivable
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            topologyKey: kubernetes.io/hostname
            labelSelector:
              matchLabels: { app: api }

# Or the newer, simpler tool for exactly this job:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: ScheduleAnyway
      labelSelector:
        matchLabels: { app: api }
Prefer "preferred" over "required"

requiredDuringScheduling anti-affinity on a three-replica Deployment in a two-node cluster leaves one pod Pending forever. preferred spreads pods when it can and still schedules when it cannot, which is almost always what you actually meant.

8

Packaging: Helm and Kustomize

Six environments times fifteen manifests is ninety files that drift. Two tools solve this, differently.

Kustomize

Built into kubectl. A base plus overlays that patch it. No templating language, so what you read is still YAML. Best for your own apps across environments.

Helm

Templated charts with a values file, versioned releases, rollback, and a huge public ecosystem. Best for installing other people's software.

both, in the form you will actually use them
# Kustomize: overlays/prod/kustomization.yaml
resources: [../../base]
namespace: prod
images:
  - name: ghcr.io/acme/api
    newTag: 1.5.0
replicas:
  - { name: api, count: 6 }
configMapGenerator:                 # name gets a content hash → auto rollout
  - name: api-config
    literals: [LOG_LEVEL=warn]

# Apply, and always look before you leap
kubectl kustomize overlays/prod         # render to stdout, review
kubectl apply -k overlays/prod

# Helm: installing something you did not write
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress ingress-nginx/ingress-nginx \
  -n ingress-nginx --create-namespace -f values.yaml
helm diff upgrade ingress ingress-nginx/ingress-nginx -f values.yaml
helm rollback ingress 1
And then GitOps

The end state most teams reach: git is the desired state, and Argo CD or Flux continuously applies it, reporting drift when the cluster disagrees. No human runs kubectl apply against production, and every change is a reviewed commit. It is beyond this course, but every habit here (declarative manifests, pinned images, overlays per environment) is exactly what it requires.

9

The pre-production checklist

Run this against any workload before it ships. Every line traces back to a module.

  • Readiness probe set, and it checks dependencies. Without it, rolling updates drop traffic. (M02)
  • Liveness probe set, and it does not check dependencies. (M02)
  • Memory request and limit set and equal. CPU request set. (M02)
  • Image pinned to a digest or an immutable tag. Never latest. (M02)
  • Replicas ≥ 2 with anti-affinity or topology spread, plus a PDB. (M07)
  • Service selector verified against real pod labels; endpoints non-empty. (M03)
  • Config and secrets injected, not baked into the image. (M04)
  • runAsNonRoot, readOnlyRootFilesystem, drop ALL capabilities. (M07)
  • Dedicated ServiceAccount, minimal RBAC, token automount off if unused. (M07)
  • terminationGracePeriod and preStop tuned so deploys do not 502. (M07)
  • Namespace has a quota and a LimitRange. (M07)
  • Logs shipped off-cluster before you need them. (M06)
  • PVC reclaim policy checked, and backups exist and have been restored once. (M05)
  • Rollback rehearsed. You have run rollout undo deliberately, at least once. (M02)
Where to go from here

You now know the fifteen objects that carry almost all day-to-day Kubernetes. The natural next steps, in order of payoff: GitOps with Argo CD or Flux, observability with Prometheus and Grafana, Gateway API as Ingress' successor, and then operators and CRDs when you have a problem that genuinely needs one. Every one of them assumes exactly what these eight modules covered.

10

Questions people actually ask

Q1Helm or Kustomize?
Kustomize for your own applications: no templating language, no {{ }} in your YAML, and it is already in kubectl. Helm for installing third-party software, where the chart is the distribution format and you only supply values. Using both is normal and not a contradiction: Helm for the ingress controller and cert-manager, Kustomize for your services.
Q2How do I give a teammate access to only their namespace?
A RoleBinding in that namespace referencing the built-in edit ClusterRole. Referencing a ClusterRole from a RoleBinding grants it only within that namespace, which is the idiom people miss. Verify with kubectl auth can-i --list --as=USER -n NAMESPACE rather than assuming.
Q3My app breaks with readOnlyRootFilesystem. Do I give up?
No: find where it writes and mount an emptyDir there. Run it once without the flag, then kubectl exec -- find / -newer /etc/hostname -type f 2>/dev/null to list what changed. Usually it is /tmp, a cache directory, and a PID file. Three emptyDir mounts and you are compliant.
Q4Why do I get 502s during every deploy?
The endpoint-removal race from section 6. Fix it with three things together: a preStop sleep of a few seconds, an application that handles SIGTERM by draining rather than exiting immediately, and maxUnavailable: 0 on the rollout so capacity never dips. Any one alone usually is not enough.
Q5Is a namespace a security boundary?
Only as far as you make it one. By itself it scopes names and nothing else: pods in different namespaces can still reach each other over the network, and share the same nodes and kernel. It becomes a boundary when you add RBAC, a ResourceQuota, NetworkPolicies and Pod Security Admission. For genuinely hostile multi-tenancy, separate clusters remain the honest answer.

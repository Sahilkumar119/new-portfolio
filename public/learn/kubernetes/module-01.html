1

What a pod actually is

A pod is one or more containers that share a network namespace and can share storage, always scheduled together onto one node. It is the smallest thing Kubernetes will place. You never schedule a container; you schedule a pod that happens to hold one.

Sharing a network namespace has a concrete consequence that trips people up: containers in the same pod reach each other on localhost, and they share one IP and one port space. Two containers in a pod cannot both bind port 8080. Containers in different pods, even on the same node, are on separate IPs entirely.

One pod — one IP, one lifecycle
container: applistens on :8080 — sees the sidecar at localhost:9090
container: log-shipperlistens on :9090 — reads the shared volume the app writes to
shared: network namespaceone pod IP, one port space, localhost between containers
shared: volumesany volume in the pod spec can be mounted by both containers
The default is one container per pod

Multi-container pods are for helpers that cannot live apart from the app: a log shipper reading the app's files, a proxy fronting it, a config reloader. If two containers could sensibly scale independently or be restarted independently, they are two pods, not one. "Frontend and backend in one pod" is the classic beginner mistake and it makes both unscalable.

Pods are cattle, and they are disposable

A pod is never repaired. If its node dies or it is evicted, it is deleted and a new pod with a new name and a new IP appears. Nothing about a pod is stable except what you deliberately make stable (a Service for the address, a PersistentVolumeClaim for the data). Write code that assumes it will be killed at any moment, because it will be.

CrashLoopBackOff is not an error, it is a symptom

It means: the container starts, exits, and Kubernetes is restarting it with an exponential backoff (10s, 20s, 40s, up to five minutes). The pod is fine. Your process is exiting. The cause is always in the previous container's output: kubectl logs POD --previous. Usually a missing env var, an unreachable dependency at startup, or a command that finishes immediately.

3

Labels and selectors: the glue

Kubernetes has no foreign keys. Objects find each other by matching labels, and that is the entire linking mechanism in the system. A Service finds its pods by selector. A Deployment owns its pods by selector. Your kubectl get filters use the same thing.

labels are how everything connects
# Pods carry labels
metadata:
  labels:
    app: checkout
    tier: backend
    env: prod

# A Service selects them
spec:
  selector:
    app: checkout      # every pod with this label is now a backend

# And so do you, on the command line
kubectl get pods -l app=checkout
kubectl get pods -l 'env in (prod,staging),tier=backend'
kubectl get pods -l '!canary'              # label absent
kubectl get pods --show-labels            # see what is actually set
kubectl label pod solo env=dev --overwrite
The failure this explains

"My Service returns connection refused and there are no endpoints." Ninety percent of the time the Service selector and the pod labels do not match, often by one character or a stale version label. kubectl get endpoints SERVICE showing <none> is the proof. Selectors are silent when they match nothing: no error, just emptiness.

Labels versus annotations

Labels are for selecting: short, indexed, queryable. Annotations are for attaching information nothing selects on: build SHAs, ingress controller settings, tool metadata, a config checksum. If you would never filter by it, it is an annotation.

4

Init containers and sidecars

Two multi-container patterns are worth knowing because both are common and neither is obvious.

initContainers

Run to completion, in order, before any app container starts. If one fails, the pod restarts it. Use for migrations, waiting on a dependency, fetching config.

Sidecars

Run alongside the app for its whole life. Log shippers, proxies, secret refreshers. Declared as an init container with restartPolicy: Always since v1.29.

pod-with-init.yaml
apiVersion: v1
kind: Pod
metadata:
  name: api
  labels: { app: api }
spec:
  initContainers:
    - name: wait-for-db          # blocks until the DB answers
      image: busybox:1.36
      command: ['sh', '-c', 'until nc -z db 5432; do sleep 2; done']
  containers:
    - name: app
      image: ghcr.io/acme/api:1.4.2
      ports:
        - containerPort: 8080
      env:
        - name: LOG_LEVEL
          value: "info"
A stuck init container looks like a stuck pod

Status Init:0/1 means your init container has not finished. The app logs are empty because the app has not started. Read the right container: kubectl logs POD -c wait-for-db. Forgetting -c is why people think a pod is producing no output at all.

The daily CLI

Roughly ten commands account for nearly all real kubectl usage. These are those ten.

CommandPurpose
kubectl get podsList. -o wide adds node and IP, -w streams changes, -A spans namespaces.
kubectl describe pod NAMEEvery field plus events. The single most useful debugging command.
kubectl logs NAME-f follow, --previous the crashed instance, -c a specific container.
kubectl exec -it NAME -- shShell inside a running container. Note the --.
kubectl apply -f DIR/Declare state, from a file or a whole directory.
kubectl delete pod NAMERemove. --force --grace-period=0 only when genuinely stuck.
kubectl port-forward pod/NAME 8080:80Tunnel a local port to a pod. How you test before a Service exists.
kubectl get events --sort-by=.lastTimestampWhat the cluster has been doing lately. Answers "why is nothing happening?".
kubectl explain pod.spec.containersField docs, offline, correct for your version.
kubectl get pod NAME -o yamlThe full object as stored, including everything the cluster filled in.

Three flags that pay for themselves immediately

the ones you will use constantly
# 1. Generate correct YAML instead of writing it from memory
kubectl run api --image=nginx:1.27 --dry-run=client -o yaml > pod.yaml
kubectl create deployment api --image=nginx:1.27 --dry-run=client -o yaml > deploy.yaml

# 2. Pull one field out with jsonpath, instead of grepping YAML
kubectl get pod api -o jsonpath='{.status.podIP}'
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.phase}{"\n"}{end}'

# 3. Alias it. You will type this thousands of times.
alias k=kubectl
source <(kubectl completion bash)   # or zsh
complete -o default -F __start_kubectl k
6

Looking inside: logs, exec, port-forward

This trio is your entire local debugging kit until Module 06 adds the systematic playbook.

debugging a live pod
# Follow logs live; --tail limits history
kubectl logs -f --tail=100 api

# The container CRASHED: this is the output that actually matters
kubectl logs api --previous

# Logs from every pod behind a label, at once
kubectl logs -l app=api --tail=20 --prefix

# Shell in. The bare -- separates kubectl flags from the command.
kubectl exec -it api -- sh
kubectl exec api -- env | sort        # one-shot, no TTY needed

# Reach the pod from your laptop with no Service involved
kubectl port-forward pod/api 8080:8080
# → curl localhost:8080 now hits the pod
port-forward is the fastest bisect in Kubernetes

App broken and you do not know which layer? Port-forward straight to the pod. If it works there, the pod is fine and your problem is the Service, the selector, or the Ingress. If it fails there too, the problem is inside the container. One command, half the search space gone.

Distroless images have no shell

exec -it -- sh fails with "executable file not found" on a slim or distroless image, and that is a good sign: your production image is small and has no shell to attack. Use kubectl debug to attach a temporary container with real tools instead (Module 06). Do not add a shell back to production just to debug it.

7

Why you almost never write a bare Pod

You have now written pod manifests, and you should stop. A bare pod is an unmanaged pod: nothing declares that it should exist, so nothing recreates it.

If this happensBare PodPod owned by a Deployment
Container exits fatallyRestarted in place, same node, foreverSame, plus replaced if the pod object dies
Node dies or drainsGone. Nothing recreates it.Rescheduled onto a healthy node
You want three copiesWrite three manifests by handreplicas: 3
You want a new versionDelete and recreate, with downtimeRolling update, with rollback
So what is a bare pod for?

Exactly two things: throwaway debugging (kubectl run tmp --rm -it --image=busybox -- sh) and learning, which is what you just did. Everything you ship is wrapped in a controller. That is Module 02, and the pod spec you just learned becomes the template section inside it, unchanged.

8

Hands-on: pods, labels, and a deliberate crash

exercise: run it, break it, read it
# 1. A pod, with a label, from a generated manifest
kubectl run web --image=nginx:1.27 --labels=app=web,env=dev
kubectl get pods -o wide --show-labels

# 2. Reach it without a Service
kubectl port-forward pod/web 8080:80 &
curl -s localhost:8080 | head -n 4
kill %1

# 3. Prove containers in a pod share localhost and one IP
kubectl exec web -- sh -c 'hostname -i; wget -qO- localhost:80 | head -n1'

# 4. Now break something on purpose: an image that does not exist
kubectl run broken --image=nginx:does-not-exist
kubectl get pod broken
kubectl describe pod broken | tail -n 15   # read the EVENTS section

# 5. And a crash loop: a container that exits immediately
kubectl run crasher --image=busybox:1.36 -- sh -c 'echo starting; exit 1'
kubectl get pod crasher -w                # watch the backoff grow, Ctrl-C
kubectl logs crasher --previous            # the output that explains it

# 6. Filter by label, then clean up by label
kubectl get pods -l env=dev
kubectl delete pod web broken crasher
  • You read an Events section and found the real cause of a failed pull.
  • You saw the restart backoff grow and read --previous logs.
  • You reached a pod through port-forward with no Service.
  • You can explain why containers in one pod share an IP but pods do not.
  • You can say why a bare pod is unsafe on a node failure.
9

Questions people actually ask

Q1Why does Kubernetes schedule pods instead of containers?
Because some containers genuinely must be co-located: they need the same localhost, the same volume, and to live and die together. A log shipper on a different node is useless. The pod is the unit that expresses "these are one deployable thing", and it keeps the scheduler's job simple: place one object, get a whole cooperating set.
Q2My pod is Running but my app is unreachable.
Running only means a process started. Check in this order: port-forward to the pod (works? then the problem is the Service or Ingress), the app is bound to 0.0.0.0 and not 127.0.0.1 (a container listening on loopback is unreachable from outside the pod), and the Service selector matches the pod labels.
Q3Does containerPort actually do anything?
Almost nothing functionally: it is documentation. Kubernetes does not block traffic to undeclared ports. It matters for readability, for tooling, and because naming a port (name: http) lets a Service target it by name instead of number, which survives the number changing. Declare it anyway.
Q4What is the pause container I see on the node?
The infrastructure container that holds the pod's network namespace. It does nothing but sleep, and your app containers join its namespace. That is the mechanism behind "containers in a pod share an IP". You will never manage it, but seeing it on a node stops it being mysterious.
Q5Why did my pod get evicted?
The node ran out of something, usually memory or disk, and the kubelet reclaimed it. Pods with no resource requests are evicted first, which is one of several reasons Module 02 insists on setting them. kubectl describe pod shows the eviction reason, and kubectl describe node shows the pressure condition that triggered it.

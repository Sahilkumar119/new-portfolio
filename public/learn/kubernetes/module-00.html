Module 00: Foundations
The Cluster & the Loop

Sahil has three containers running happily on one machine with Docker Compose. Then traffic triples, the machine reboots at 2am, and nothing comes back up. This module is the answer to that night: what Kubernetes actually is, the one loop that explains all of its behaviour, and the parts of a cluster you will name in every interview you ever sit.

~1.5h · concepts first assumes Docker basics mental model + first pod Kubernetes v1.34
0

The problem orchestration solves

Docker gave Sahil one great thing: a container that runs identically everywhere. It gave him nothing at all for the questions that follow. Who restarts the container when it dies? What happens when one machine is not enough? How does traffic find the three copies instead of the one? How do you deploy a new version without going dark for thirty seconds?

Every one of those has an obvious manual answer and a terrible manual outcome. Orchestration is the decision to stop answering them by hand.

Self-healing

Container dies, node dies, process hangs. Kubernetes notices and replaces it without paging anyone.

Scaling & scheduling

You say "five copies". It decides which machines have room and places them there.

Stable networking

Pods get new IPs constantly. A Service gives them one name and address that never moves.

Be honest about the cost

Kubernetes is not free. It adds a control plane, a YAML surface, and a genuinely steep first month. For one small app on one machine, Compose is the right answer and reaching for Kubernetes is resume-driven development. The break-even lands around: multiple services, more than one machine, and a real uptime expectation.

1

What Kubernetes actually is

Strip away every feature and one sentence remains:

The whole system, in one line

Kubernetes is a desired-state engine. You declare what should be true. Controllers watch what is true. When the two differ, they act to close the gap, forever, in a loop.

This is the single idea that makes the rest of Kubernetes predictable. You never tell Kubernetes to do something. You tell it what the world should look like, and it works out the verbs. Delete a pod that a Deployment owns and a new one appears within seconds, not because deletion failed but because you never changed the desired state: you only disturbed the actual one.

Why your deleted pod came back

The most common day-one confusion. kubectl delete pod web-7d4 succeeds, and a pod named web-9x2 appears. Nothing is broken. You deleted an actual object while the desired count stayed at three. To really remove it, change the desire: delete the Deployment, or scale it to zero.

2

Cluster anatomy

A cluster is two kinds of machine. The control plane decides. The nodes run your containers. That is the whole split, and every component below belongs firmly to one side.

Control plane — the brain
kube-apiserverThe only door in. Every read and write, from kubectl or from a controller, goes through it. Validates, authenticates, persists.
etcdThe database. A key-value store holding the entire cluster state. Lose etcd and you lose the cluster.
kube-schedulerWatches for pods with no node assigned, picks a node based on resources, affinity and taints, writes the choice back.
controller-managerRuns the reconciliation loops: Deployment, ReplicaSet, Node, Job and dozens more.
Every node — the muscle
kubeletThe agent on each machine. Asks the API server "what should run here?", tells the container runtime to make it so, and reports health back.
kube-proxyPrograms the node's network rules so Service IPs actually route to pod IPs.
container runtimecontainerd or CRI-O. Actually pulls images and starts containers. This is where Docker's job ended up.
The one sentence to remember

Nothing talks to anything except through the API server. The scheduler does not phone the kubelet. The kubelet does not phone the scheduler. They all read and write the API server, and etcd sits behind it. That hub-and-spoke shape is why Kubernetes is extensible: a new controller is just another client.

Where did Docker go?

Kubernetes removed the Docker-specific shim in v1.24. It now talks to any runtime implementing the Container Runtime Interface, usually containerd, which is the same engine Docker itself uses underneath. Your images are unaffected: they are OCI images, and Docker builds them fine. Nothing you learned about Dockerfiles is wasted.

Objects, and the shape every YAML shares

Everything in Kubernetes is an object in the API. Pods, Services, Secrets, even Nodes. And every single one, without exception, has the same four top-level fields. Learn this shape once and you can read any manifest you will ever be handed.

apiVersion: apps/v1which API group + version kind: Deploymentwhat type of object metadata:name, namespace, labels spec:your desired state
FieldWhat it isWho writes it
apiVersionAPI group and version. v1 for core objects (Pod, Service, ConfigMap), apps/v1 for workloads.You
kindThe object type. Capitalised, singular.You
metadataIdentity: name, namespace, labels, annotations.You
specThe desired state. Everything specific to this kind lives here.You
statusThe observed state. Never write it.Kubernetes
pod.yaml · the smallest real manifest
apiVersion: v1
kind: Pod
metadata:
  name: hello
  labels:
    app: hello
spec:
  containers:
    - name: web
      image: nginx:1.27
      ports:
        - containerPort: 80
YAML will bite you before Kubernetes does

Indentation is two spaces, never tabs. A list item is - with a space. on, yes and no parse as booleans, so quote them when you mean strings. Port numbers are integers, image tags are strings, and "8080" in a place expecting a number is a rejected manifest.

kubectl, your only tool

One binary talks to the API server. Everything you do in this course goes through it. The verbs you need on day one:

CommandDoes
kubectl apply -f file.yamlSend desired state to the cluster. Creates or updates. The command you will use most.
kubectl get podsList objects. Add -o wide for node and IP, -w to watch live.
kubectl describe pod NAMEFull human-readable detail plus recent events. Your first debugging stop.
kubectl logs NAMEContainer stdout/stderr.
kubectl delete -f file.yamlRemove what that file declares.
kubectl explain pod.specBuilt-in field docs. Works offline, always matches your cluster version.
kubectl api-resourcesEvery object kind this cluster knows, with its short name and apiVersion.

Context and namespace: the two settings that cause the most damage

A context is "which cluster, as which user, in which namespace". Running the right command against the wrong context is the classic production incident, and it looks exactly like a successful command.

know where you are before you type anything
# Which cluster am I pointed at right now?
kubectl config current-context

# List all contexts you have credentials for
kubectl config get-contexts

# Switch cluster, and set a default namespace so you stop typing -n
kubectl config use-context kind-dev
kubectl config set-context --current --namespace=demo

# Everything in the cluster, all namespaces (the "what is even running" view)
kubectl get all -A
Habit worth building today

Put the current context and namespace in your shell prompt (kube-ps1, or starship's kubernetes module). It costs ten minutes once and removes an entire category of outage. Sahil learned this by scaling a production deployment to zero while believing he was on staging.

5

What kubectl apply really does

Be able to narrate this end to end. It is the most common interview question in the whole subject, and more usefully, it tells you exactly where to look when a pod never starts.

  1. kubectl → API server. Your YAML becomes an HTTP request. The API server authenticates you, checks RBAC, validates the schema, runs admission controllers, and writes the object to etcd. At this instant kubectl prints created and exits. Nothing is running yet.
  2. Deployment controller sees a Deployment with no matching ReplicaSet and creates one.
  3. ReplicaSet controller sees it needs 3 pods and has 0, so it creates 3 Pod objects. They have no node assigned: their status is Pending.
  4. Scheduler watches for unassigned pods, filters nodes that could fit (resources, taints, affinity), scores the survivors, and writes nodeName onto each pod.
  5. kubelet on that node sees a pod assigned to it, tells containerd to pull the image and start the containers, then reports status back to the API server.
  6. Status flows back. Pending → ContainerCreating → Running. kubectl get pods is just reading what the kubelet wrote.
Why this trace is a debugging tool

The stage a pod is stuck in tells you which component to blame. Stuck Pending means the scheduler could not place it: no node has room, or a taint blocks it. Stuck ContainerCreating or ImagePullBackOff means the scheduler did its job and the kubelet cannot: bad image name, missing registry credentials, a volume that will not mount. You have narrowed the problem before reading a single log line.

6

Get a cluster on your laptop

You do not need a cloud account, and you should not learn on one. Pick one of these and move on.

kind

Runs nodes as Docker containers. Fastest to start, trivial to throw away, easy multi-node. The recommendation for this course.

minikube

A single-node VM or container with useful addons (ingress, metrics-server, dashboard) one command away.

Docker Desktop

Already installed for many people. One checkbox in settings. Least control, least setup.

a two-node cluster in about a minute
# kind: nodes are containers, so Docker must be running
kind create cluster --name dev

# Or with a worker node, so scheduling is actually interesting
cat <<EOF | kind create cluster --name dev --config=-
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
EOF

# Prove it works. kind wires up your kubeconfig automatically.
kubectl get nodes
NAME                STATUS   ROLES           AGE   VERSION
dev-control-plane   Ready    control-plane   47s   v1.34.0
dev-worker          Ready    <none>          31s   v1.34.0

# Done for the day? Delete the whole cluster, no residue.
kind delete cluster --name dev
Local clusters are for learning, not lying to yourself

A local cluster fakes two things badly: LoadBalancer services (no cloud to provision one) and real storage classes. Everything else in this course behaves identically. Module 03 shows the workaround for the first, Module 05 for the second.

7

Hands-on: watch the loop fight you

The point of this exercise is not to run nginx. It is to see, with your own eyes, that Kubernetes ignores your actions and obeys only your declarations.

exercise: desired state versus actual state
# 1. A bare pod. Nothing owns it, nothing protects it.
kubectl run solo --image=nginx:1.27
kubectl get pods

# 2. Delete it. It stays dead: nothing declared that it should exist.
kubectl delete pod solo
kubectl get pods

# 3. Now a Deployment: a declaration of "3 of these should exist"
kubectl create deployment web --image=nginx:1.27 --replicas=3
kubectl get pods -w          # watch them come up, then Ctrl-C

# 4. Kill one on purpose. Watch a replacement appear in seconds.
kubectl delete pod "$(kubectl get pods -l app=web -o name | head -n1)"
kubectl get pods

# 5. Read the object Kubernetes wrote back at you: note .status
kubectl get deployment web -o yaml | head -n 40

# 6. Change the DESIRE, and the pods actually go away
kubectl scale deployment web --replicas=0
kubectl get pods

# 7. Clean up
kubectl delete deployment web
  • You watched a deleted pod get replaced, and can say exactly why.
  • You can name the four control plane components and what each decides.
  • You can name the three things on every node.
  • You can write the four fields every manifest has, from memory.
  • You know which component to suspect when a pod is stuck Pending.
8

Questions people actually ask

Q1Is Kubernetes replacing Docker?
No, and the two barely compete. Docker is how you build an image and run one container on one machine. Kubernetes is how you run many containers across many machines. Kubernetes dropped the Docker-specific runtime shim in v1.24 and speaks to containerd directly, but it still runs the exact OCI images your docker build produces.
Q2Why is everything YAML instead of a real language?
Because manifests are data, not instructions. Data can be diffed, reviewed in a pull request, stored in git, and applied twice with the same result. That last property, idempotency, is what makes apply safe to run in a loop. When YAML becomes painful at scale, the answer is a tool that generates it (Kustomize, Helm) rather than a different runtime format.
Q3What is a namespace, really?
A name scope inside one cluster, not a security boundary by itself. Two objects can share a name if they are in different namespaces, and DNS, quotas and RBAC all key off it. Note that some objects are cluster-scoped and live outside any namespace: Nodes, PersistentVolumes, StorageClasses, ClusterRoles. kubectl api-resources --namespaced=false lists them.
Q4apply, create, or edit?
apply for everything real: declarative, idempotent, works from files in git. create is imperative and fails if the object exists; it is handy for quick scratch objects and for generating YAML with --dry-run=client -o yaml. edit opens the live object in your editor and is a debugging tool only: your change vanishes the next time someone applies the file.
Q5How much of the API do I actually need?
Roughly fifteen kinds carry almost all day-to-day work: Pod, Deployment, ReplicaSet, Service, Ingress, ConfigMap, Secret, Namespace, PersistentVolumeClaim, StatefulSet, DaemonSet, Job, CronJob, ServiceAccount, and Role/RoleBinding. That list is this entire course. Everything else you can look up with kubectl explain on the day you need it.

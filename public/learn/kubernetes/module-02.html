The ownership chain

Three objects, one direction of control. Understanding this chain explains every rollout behaviour you will ever see, including the strange ones.

Why you see old ReplicaSets with 0 pods

They are your rollback history. Each change to the pod template creates a new ReplicaSet and scales the previous one to zero rather than deleting it. kubectl rollout undo works by scaling an old one back up. Keep the count sane with revisionHistoryLimit (default 10).

A change to what, exactly?

A new ReplicaSet is created only when the pod template changes: image, env, resources, labels, volumes. Changing replicas is not a template change, so scaling does not create a revision and cannot be rolled back through rollout history. That distinction confuses people the first time they scale and then try to undo.

2

The manifest, field by field

The pod spec you learned in Module 01 reappears here verbatim, nested under spec.template. Nothing new to learn about containers; only the wrapper is new.

deployment.yaml · the shape you will write a thousand times
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  revisionHistoryLimit: 5
  selector:                     # which pods this Deployment owns
    matchLabels:
      app: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1              # extra pods allowed above replicas
      maxUnavailable: 0        # never dip below replicas → zero-downtime
  template:                     # ← everything below is a Pod spec
    metadata:
      labels:
        app: api               # MUST match selector.matchLabels
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/api:1.4.2
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { memory: "256Mi" }
          readinessProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 5
selector is immutable

Once created, spec.selector cannot be changed. An apply that tries will be rejected and your only fix is to delete and recreate the Deployment, which means downtime. Choose a stable, minimal selector on day one (app: api), and put volatile things like version in the template labels only.

3

How a rolling update actually moves

You change the image tag and apply. Kubernetes creates a second ReplicaSet and walks the two counts in opposite directions, bounded by two numbers.

FieldMeaningEffect
maxSurgeHow many pods above replicas may exist mid-rollout.Higher = faster rollout, more peak resource use.
maxUnavailableHow many pods below replicas may be unavailable.0 = never lose capacity. The safe production value.

With replicas: 3, maxSurge: 1, maxUnavailable: 0, the sequence is: start one new pod (4 total), wait for it to become Ready, kill one old pod (3 total), repeat. Capacity never drops below three. Both values also accept percentages, which is what you want once replica counts vary between environments.

Zero-downtime depends entirely on your readiness probe

The rollout advances when a new pod reports Ready. With no readiness probe, "Ready" means "the process started", so Kubernetes cheerfully kills a healthy old pod and sends traffic to a new one that is still loading. A rolling update without a readiness probe is a rolling outage. That single sentence is the most valuable thing in this module.

Recreate strategy

strategy.type: Recreate kills every old pod before starting any new one. It causes real downtime, and it is the correct choice when old and new versions genuinely cannot coexist: an incompatible schema migration, or a single writer holding an exclusive lock on a volume.

4

Driving a rollout from the CLI

the deploy loop
# Ship a new version (edit the tag in git and apply; this is the quick way)
kubectl set image deployment/api api=ghcr.io/acme/api:1.5.0

# Watch it. This BLOCKS until done and exits non-zero on failure,
# which is exactly what you want in a CI pipeline.
kubectl rollout status deployment/api --timeout=120s

# It went wrong. Back to the previous revision, now.
kubectl rollout undo deployment/api

# Or to a specific one
kubectl rollout history deployment/api
kubectl rollout undo deployment/api --to-revision=3

# Pause mid-rollout to inspect, then resume (a poor man's canary)
kubectl rollout pause deployment/api
kubectl rollout resume deployment/api

# Restart every pod without changing anything (picks up a new Secret/ConfigMap)
kubectl rollout restart deployment/api

# Scale
kubectl scale deployment/api --replicas=5
Record your intent in git, not in the cluster

set image is fine for a hotfix but it makes the cluster disagree with your repository, and the next apply silently reverts it. In any real workflow the image tag changes in a file, the file is reviewed, and CI runs apply then rollout status. The cluster should never be the source of truth.

progressDeadlineSeconds

If a rollout makes no progress for this long (default 600s), the Deployment is marked failed and rollout status returns an error. It does not auto-roll-back. Your pipeline has to notice the non-zero exit and call undo itself. Plenty of teams discover this during their first bad deploy.

5

The three probes

Kubernetes cannot know whether your process is healthy. It only knows whether it is running. Probes are how you tell it the difference, and each of the three answers a different question.

readinessProbe

Should traffic go here? Fails: pod is removed from Service endpoints but keeps running. The one you must always set.

livenessProbe

Is this process wedged? Fails: the container is killed and restarted. Powerful and easy to misuse.

startupProbe

Has it finished booting? While it runs, the other two are suspended. For slow-starting apps.

a probe set that will not hurt you
startupProbe:                    # up to 30 x 5s = 150s to boot
  httpGet: { path: /healthz, port: http }
  failureThreshold: 30
  periodSeconds: 5

readinessProbe:                  # checks DEPENDENCIES too: DB, cache
  httpGet: { path: /readyz, port: http }
  periodSeconds: 5
  failureThreshold: 3

livenessProbe:                   # checks ONLY "is this process wedged"
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
  failureThreshold: 3            # 30s of failure before a kill
The outage amplifier

Never let a liveness probe check a dependency. If /healthz queries the database and the database has a slow minute, every replica fails liveness, every replica is killed at once, and a small database blip becomes a total outage with a thundering-herd restart on top. Liveness answers "is this process stuck?" and nothing else. Dependencies belong in readiness, where failure only removes you from load balancing until things recover.

Probe typeUse when
httpGetAnything that serves HTTP. Any 2xx or 3xx is a pass. The default choice.
tcpSocketNon-HTTP servers: databases, queues. Only proves the port is open.
execA command in the container; exit 0 passes. Most expensive: it forks a process every period.
grpcNative gRPC health checking protocol, stable since v1.27.
6

Requests and limits

Two numbers per resource, doing completely different jobs. Conflating them is the second most common production mistake in this module.

requests

Scheduling. "Reserve this much for me." The scheduler adds up requests to decide if a node has room. It is a guarantee of availability, not a cap.

limits

Enforcement. "Never let me exceed this." CPU over limit is throttled. Memory over limit is killed, instantly, with no grace.

ResourceOver the limitSensible practice
CPU (100m = 0.1 core)Throttled. Slow, never killed. CPU is compressible.Always request. Often omit the limit: throttling a healthy app to enforce a guess helps nobody.
Memory (128Mi)OOMKilled immediately. Memory cannot be reclaimed gently.Always set both, and set them equal for anything important.

QoS classes, and who dies first

Kubernetes derives a class from what you set, and uses it to pick eviction victims when a node runs short:

ClassYou setEvicted
Guaranteedrequests == limits, for every resource and containerLast. Use for anything that matters.
Burstablerequests set, limits higher or absentMiddle. The common case.
BestEffortnothing set at allFirst. Never ship this.
How to pick the numbers

Do not guess twice. Ship with a rough guess, then read real usage with kubectl top pod over a normal day. Set the memory request and limit equal, at roughly peak plus 25%. Set the CPU request at typical usage and leave the CPU limit off unless you are deliberately protecting noisy neighbours. Revisit after any significant change.

Reading an OOMKill correctly

kubectl describe pod shows Last State: Terminated, Reason: OOMKilled, Exit Code: 137. That is the kernel, not Kubernetes, and it is not a bug in your app unless your app really does leak. It means the container touched its memory limit. Raise the limit or fix the usage, but note that the logs will show nothing: there is no warning before a SIGKILL.

7

The other workload controllers

Deployment covers most of what you run. Four siblings cover the rest, and they all wrap the same pod template.

KindGuaranteesUse for
DeploymentN interchangeable pods, rolling updates, rollbackStateless services. Your default.
StatefulSetStable names (db-0, db-1), ordered start-up, one persistent volume per podDatabases, queues, anything with identity. Module 05.
DaemonSetExactly one pod on every node, including new onesLog collectors, node exporters, CNI agents.
JobRun to successful completion N times, then stopMigrations, batch work. Module 06.
CronJobCreates a Job on a scheduleBackups, nightly reports. Module 06.
Default to Deployment

StatefulSet is slower to roll, harder to debug, and awkward to scale down. Reach for it only when you genuinely need stable identity or per-pod storage. Plenty of teams put a stateless API in a StatefulSet "because it feels more serious" and inherit the pain for nothing.

8

Hands-on: ship, break, roll back

exercise: a full deploy cycle including a failed one
# 1. Create a Deployment and watch the ownership chain appear
kubectl create deployment api --image=nginx:1.26 --replicas=3
kubectl get deploy,rs,pods

# 2. A good rollout. Watch pods swap one at a time.
kubectl set image deployment/api nginx=nginx:1.27
kubectl rollout status deployment/api
kubectl get rs        # old RS is now 0, kept for rollback

# 3. A BAD rollout: an image that will never pull
kubectl set image deployment/api nginx=nginx:9.9.9-nope
kubectl rollout status deployment/api --timeout=40s   # fails
kubectl get pods    # note: the 3 OLD pods are still serving. maxUnavailable saved you.

# 4. Roll back and confirm
kubectl rollout undo deployment/api
kubectl rollout status deployment/api
kubectl rollout history deployment/api

# 5. Prove memory limits are enforced by the kernel, not politely
kubectl run oom --image=polinux/stress --restart=Never \
  --limits=memory=64Mi -- stress --vm 1 --vm-bytes 200M --timeout 30s
kubectl get pod oom
kubectl describe pod oom | grep -A3 'Last State'   # OOMKilled, exit 137

# 6. Clean up
kubectl delete deployment api; kubectl delete pod oom
  • You saw Deployment → ReplicaSet → Pod with your own eyes.
  • A failed rollout did not take down the running version.
  • You rolled back in one command and read the revision history.
  • You produced a real OOMKill and found exit code 137.
  • You can explain why liveness must not check the database.
9

Questions people actually ask

Q1Readiness or liveness: which do I set if I only set one?
Readiness, without hesitation. It gives you safe rolling updates and keeps traffic away from pods that cannot serve. Liveness only helps with a genuinely wedged process that will never recover, which is rarer than people assume, and a badly written liveness probe actively causes outages. Add liveness second, conservatively.
Q2Why did nothing happen when I applied my change?
Almost always because the pod template did not change. Editing a ConfigMap that the pods mount does not touch the Deployment, so no new ReplicaSet is created and no pods restart. Either kubectl rollout restart, or add a checksum annotation of the config into the pod template so a config change becomes a template change (Module 04).
Q3Should I set a CPU limit?
Usually not, and this is a genuinely contested opinion. A CPU limit throttles your app even when the node has idle cores, which turns spare capacity into latency for no benefit. Set CPU requests so the scheduler places you correctly, and add a limit only in multi-tenant clusters where you must protect neighbours from a runaway process. Memory is the opposite: always limit it.
Q4How do I do a canary or blue-green deploy?
Plain Kubernetes gives you a crude version for free: run two Deployments whose pods share a Service selector label, and control the traffic split by their relative replica counts. Nine old pods and one new pod is a 10% canary. Anything more precise (header-based routing, automated rollback on metrics) needs Argo Rollouts, Flagger, or a service mesh. Out of scope here, and correctly so.
Q5Why is my pod Ready 0/1 but not restarting?
The readiness probe is failing while liveness passes, which is the system working exactly as designed: the pod is alive but not serving, so it stays up and receives no traffic. Check the probe path, the port, and whether the app is actually listening on 0.0.0.0. Then check whether a dependency your /readyz endpoint queries is down.
